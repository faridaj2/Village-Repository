# User Preferences
- Communicates in Bahasa Indonesia (Indonesian). Confidence: 0.9
- Gives very brief instructions (e.g. "baca dan lakukan") and expects the agent to read project docs and autonomously execute the full plan without asking clarifying questions. Confidence: 0.9
- Prefers the agent to work through an entire task list end-to-end without pausing for confirmation. Confidence: 0.85
- Prefers modern, polished UI: gradient stat cards with colored shadows, donut charts, SVG status icons (not emoji), rounded-2xl cards, and clean card-based layouts. Confidence: 0.9
- Wants comprehensive, full-page redesigns done all at once ("semuanya dibuat modern") rather than incremental tweaks. Confidence: 0.85
- Favors indigo/purple gradient as primary accent (`from-indigo-500 to-purple-600`) with matching colored shadows. Confidence: 0.85
- Prefers borderless filled inputs (`bg-gray-50 border-0 rounded-xl`) over traditional bordered inputs. Confidence: 0.8
- Likes collapsible sidebar with icon-based navigation, section labels, and glassmorphism topbar (`backdrop-blur-xl`). Confidence: 0.8
- Prefers button-based filter groups (toggle buttons) over dropdown selects for geographic/administrative filtering like RW/RT selection on maps. Confidence: 0.8
- Wants geographic/administrative boundary visualization on maps (outlines, polygons per RW/RT) with color-coded regions. Prefers hierarchy Desa → RW → RT (no Dusun concept); RW and RT are separate entities with their own boundaries, each can have multiple entries. Confidence: 0.9
- Prefers simple copy-paste GeoJSON textarea input for geographic boundary data over complex interactive map-drawing tools. Uses geojson.io to create GeoJSON. Confidence: 0.8
- Prefers separate fields over overloading existing enums when adding new categorization dimensions (e.g. kept `status` for aktif/pindah/meninggal and added a new `jenis_penduduk` field for penduduk/pendatang instead of merging them). Values clean separation of orthogonal concepts in data modeling. Confidence: 0.9
- Prefers dedicated modules for distinct organizational concepts rather than embedding related data into existing entities. E.g. removed ketua_rw/ketua_rt fields from RT/RW models and created a separate "Struktur Pemerintahan" module instead. Will quickly pivot and reverse decisions if a better architectural approach emerges. Confidence: 0.85
- Expects feature parity across related views: when a field (e.g. RT/RW) is added to list/detail views, it must also be present in create/edit forms. Will point out missing fields immediately. Confidence: 0.85
- Prefers dynamic, image-rich hero sections on public-facing pages (e.g. photo sliders/carousels with auto-play, overlays, and CTA buttons) over static text-only hero blocks. Confidence: 0.8
- Prefers key-value settings storage with a single JSON `value` column (e.g. `admin_settings` table with `key` + `json value`) over individual columns per setting. Wants admin-configurable settings (site name, hero sliders, etc.) stored this way and exposed via a dedicated admin settings page. Confidence: 0.85
- Prefers vanilla JavaScript over Alpine.js for interactive components — Alpine.js has proven unreliable in this project: `x-for` templates, `:class` opacity toggles, and `:style` inline bindings all caused bugs (e.g. `:style` margin-left ignoring responsive breakpoints). Use Tailwind responsive classes and plain JS instead. Confidence: 0.9
- Prefers image-only hero sliders without text overlays — wants clean photo slides with just CTA buttons below, no title/subtitle text on the slides themselves. Confidence: 0.8
- Expects clear, visible error/feedback messages in the UI when operations fail (e.g. login errors, form validation). Will immediately flag silent failures where the user gets no feedback. Confidence: 0.85
- Prefers optional entity relationships with toggle/checkbox UI: when linking entities (e.g. penduduk → rumah), the relationship should be nullable and enabled via a toggle switch, not mandatory. This lets users enter partial data without being blocked by required fields. Confidence: 0.8
- Expects form fields to be grouped by the entity they semantically belong to, not loosely placed where convenient. E.g. "miskin" (personal status) stays in Data Pribadi, while latitude/longitude (physical location) go in Rumah — even if the assistant thinks another grouping looks better. Will immediately correct misplaced fields. Confidence: 0.9
- Expects visual diagrams/charts (e.g. org chart, structure tree) to be included when building organizational or structural modules — not just list/table views. Will immediately ask "mana bagannya" if a visual representation is missing. Confidence: 0.8
- Expects organizational charts to support explicit parent-child hierarchy via `parent_id` (not just `urutan` grouping). Wants full control over who is below whom and who is parallel. Uses `parent_id` for vertical hierarchy (who reports to whom) and `urutan` for horizontal ordering within the same level. Items with no parent are root-level peers. Confidence: 0.9
- Says "push" to mean the full git workflow: add the changed file(s), write a descriptive commit message, and push — expects the agent to infer which files and craft an appropriate message without further input. Confidence: 0.9
- Deploys to shared hosting without Node.js — frontend assets (Vite/npm) must be built locally and the `public/build` directory committed to git. The agent should never suggest running `npm` on the server. Confidence: 0.95
